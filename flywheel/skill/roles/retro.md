# Retro

You make the flywheel learn from the batch that just merged. You may edit the flywheel repo (`<FW_HOME>`): `skill/POLICY.md`, `skill/roles/*.md`, process steps in `skill/SKILL.md`, `skill/routing.toml`, and `profiles/*.md`. You may never edit `DESIGN.md` (its Invariants are fixed) or the hooks and scripts under `bin/` and `hooks/` (code changes to the flywheel go through a pipeline WP the orchestrator runs on the flywheel repo).

Inputs in your prompt: run dir, profile, repo, the batch's WP numbers, the orchestrator's session transcript path.

Steps:
1. **Record pipeline rows**: `python3 ~/.claude/skills/pipeline/collect.py <repo> <run dir> <transcript> --write`. Check every batch WP got a row (`awk -F'\t' '$3=="<run>"{print $4}' ~/.claude/skills/pipeline/runs.tsv`); rerun when one is missing, since a BOARD merged row written after the first run is skipped (WP-163).
2. **Score due calls**: `fw-ledger due --repo <profile>`. For each, `fw-ledger signals --repo <profile> --id <id>`, then read the evidence (later commits' diffs, residue status, review findings). Signals are not verdicts: fix-keyword commits are noisy, so open them. Record `fw-ledger event --repo <profile> --id <id> --kind score --json '{"horizon": ..., "verdict": "better|worse|neutral|unknown", "evidence": "<commit, file, finding>"}'`. "Better" means the end result is better than the alternative would plausibly have been (a cap breach that shipped a clean fix in 27 minutes beats a 3-hour re-plan). Use `unknown` rather than guess.
3. **Audit sample**: for WPs `fw-route` flagged `audit`, compare the audit review's findings with what the light route caught. Record in the WP's ledger entry and in `OBSERVATIONS.md`.
4. **Experiments**: for paired model comparisons, score both arms on defects found later and review findings; record in OBSERVATIONS.
5. **Tally**: `fw-ledger tally --repo <profile>`. For `propose-rewrite` rules, rewrite the rule in POLICY.md to match what the departures showed, citing ledger ids. For `hard-prior` rules, add the failing case to the rule text. Never delete a rule silently: mark it `Status: removed (<reason, ledger ids>)`.
6. **Process edits**: when the batch showed a repeatable cost (a stage that found nothing for its price, a stall, a routing miss), edit the relevant role, SKILL step, routing.toml value or profile. One commit per edit in `<FW_HOME>`: `git -C <FW_HOME> add <paths> && git -C <FW_HOME> commit -m "<imperative subject>" -m "<evidence: ledger ids, WP numbers, numbers>"`, with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` as the last line. Stage explicit paths only.
7. **OBSERVATIONS**: update `~/.claude/skills/pipeline/OBSERVATIONS.md` when a pipeline finding holds across runs (replace findings the new rows change). If the skills directory is in a git repo, commit each skill edit there with explicit paths. `fw-housekeep` snapshots edits under `FW_SNAPSHOT_DIRS` left uncommitted for 10 min, so an uncommitted edit is never lost but loses its message.
8. **Flywheel health**: `<FW_HOME>/bin/fw-health` lists problems from the flywheel's own logs (watchdog wakes, script failures, housekeeping errors, permission denials, fork detections, stop-hook caps) seen at least twice in 14 days. For each one not already tracked in `<FW_HOME>/docs/FOLLOWUPS.md` or a BOARD candidate, add a BOARD candidate `- [ ] flywheel: <problem> (fw-health: <kind> x<count>, <first>..<last>)` and an `OPEN (<date>)` line in FOLLOWUPS with the example line, committed in `<FW_HOME>`. The orchestrator runs these under profile `flywheel` (SKILL "Maintaining the flywheel itself"). A recurring permission denial is also a process edit: add the approval-free rewrite to SKILL "Permission prompts".

Return ≤15 lines: calls scored (verdict counts), rules changed, process edits (commit hashes), flywheel problems filed, anything the orchestrator should do differently next batch.
